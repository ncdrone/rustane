# Stage 5: Decode Optimization III — 19.6 → 30+ tok/s

> Research from 6-agent audit + old framework analysis (ane-infer, uzu, flash-moe).
> Date: 2026-03-21. Current: 19.6 tok/s decode, 310ms prefill, 20/20 HF match.

## Current Bottleneck (51ms/token)

```
Metal MoE dispatch:  ~31ms (60%)  ← 27ms compute + 4ms cmd_buf overhead (48 commits)
CPU attention:       ~25ms (38%)  ← 4×sgemv + softmax + scores, 48 layers
Everything else:      ~1ms (2%)
```

Theoretical ceiling: ~88 tok/s (bandwidth-limited at 400 GB/s). Current utilization: ~22%.

## Key Insight from Old Frameworks

**ane-infer (32 tok/s Q8 on M5):** Creates ONE `MTLCommandBuffer` for the entire token across all 48 layers. Each operation gets its own `MTLComputeCommandEncoder` within that buffer. ONE `commit()` + `waitUntilCompleted()` per token. This eliminates 47 × 85µs = 4ms of pure commit overhead.

**uzu (40+ Metal shaders):** Has online softmax attention — single-pass FlashAttention-style kernel that computes QK^T + softmax + V-weighted-sum in one dispatch. Also has quantized GEMV with fast path when output%8==0 AND input%512==0.

**ane-infer's FusedTripleProjection:** WQ+WK+WV in one dispatch (ANE prefill). Our ANE prefill already does this, but decode doesn't batch QKV at all.

## Ranked Recommendations

### R1. Batched QKV Projection (3 sgemv → 1)
**Expected: -2.4ms/token → 20.6 tok/s. Risk: Very low.**

Currently 3 separate `cblas_sgemv` calls per layer for Q/K/V:
- Q: [4096, 2048] × [2048]
- K: [512, 2048] × [2048]
- V: [512, 2048] × [2048]

All share the same input x[2048]. Concatenate weights vertically: W_qkv = [5120, 2048]. One sgemv produces [5120], sliced into Q[0:4096], K[4096:4608], V[4608:5120].

Saves ~30µs/layer call overhead + better AMX pipelining = ~50µs/layer × 48 = 2.4ms.

**Implementation:** Add `qkv_proj: Vec<f32>` to `LayerAttnF32`, concatenate at load time. New `gqa_forward_f32_batched_qkv()` in attention.rs.

### R2. Single Command Buffer for ALL 48 Layers
**Expected: -4ms/token → 22.4 tok/s. Risk: Medium.**

Currently 48 separate `commit()` + `waitUntilCompleted()` per token (one per layer's MoE). Each commit costs ~85µs = 4ms total.

**The dependency chain:** Layer N's MoE output feeds layer N+1's RMSNorm → attention. If attention stays on CPU, we can't encode all 48 layers into one cmd_buf because CPU attention must run between Metal MoE dispatches.

**But:** If we also move attention projections to Metal (R4), then the ENTIRE 48-layer forward pass can be one cmd_buf. The only CPU work between layers would be: (a) RMSNorm (trivial, ~1µs/layer), (b) attention scores + softmax (scalar, ~100µs/layer), (c) MoE routing (trivial, ~10µs/layer).

**Standalone implementation (without R4):** Not possible. The CPU-GPU sync between MoE and attention prevents merging.

**Combined with R4:** One cmd_buf encodes: Q_proj + K_proj + V_proj + [CPU attention scores] + O_proj + fused_gate_up_silu + down for all 48 layers. The CPU attention scores are the only serial dependency.

### R3. Eliminate 240 Allocations/Token in Attention
**Expected: -1.5ms/token → 23.2 tok/s. Risk: Low.**

`gqa_forward_f32` allocates ~5 Vecs per call (q, k, v, concat, output) = 240 allocations per token.
- `matvec_f32_direct()` allocates `vec![0.0f32; out_dim]` every call
- `f32_from_f32_slice()` copies norm weights unnecessarily
- `single_head_attention()` allocates `head_out` per head = 32 × 48 = 1536 allocs

**Fix:** Pre-allocate decode-path buffers in Model (or pass a reusable workspace). Clear instead of alloc. Pass norm weight slices directly.

### R4. Metal f32 SGEMV for Attention Projections
**Expected: -5 to -10ms/token → 26-30 tok/s. Risk: Medium. HIGHEST LEVERAGE.**

Write a simple f32 sgemv Metal shader (no dequant — attention weights are f32). Encode Q+K+V+O projections for ALL 48 layers into the same cmd_buf as MoE dispatches.

The entire token becomes:
```
CPU: embed lookup
Metal (ONE cmd_buf): for each of 48 layers:
  encode Q_proj, K_proj, V_proj dispatches
  barrier (wait for proj results)
  CPU reads Q,K,V → attention scores → attention output (can't avoid)
  encode O_proj dispatch
  barrier
  encode fused_gate_up_silu dispatches
  encode down dispatches
commit() + waitUntilCompleted()
CPU: final norm + LM head + sample
```

Wait — this doesn't work cleanly because Metal cmd_buf can't interleave with CPU reads. Alternative architecture:

**Hybrid approach:** Keep attention on CPU but move ONLY the projection sgemv to Metal. The Q/K/V/O projections are 4 matrices × 48 layers = 192 sgemv calls. Currently these go through AMX (~520µs/layer). If Metal can do them faster (by avoiding sgemv call overhead and batching), this saves time.

Actually, the real question: **is Metal f32 sgemv faster than AMX for [4096,2048] × [2048]?** At 2048 hidden × 4096 out = 33.5M float ops. AMX does this in ~120µs (benchmarked). Metal dispatch overhead alone is ~85µs for a commit. Single Metal sgemv would need to be <35µs compute to beat AMX, and the matrix is 32MB — bandwidth-limited at ~80µs minimum.

**Revised verdict:** For individual sgemv, AMX beats Metal due to lower dispatch overhead. The win from Metal is ONLY if we can batch 192 sgemv calls into one cmd_buf and overlap with other Metal work. But the serial dependency (attention scores need Q/K/V results) prevents full batching.

**Better approach: Batch Q+K+V into one Metal dispatch per layer (R1 on Metal).** Encode a triple-GEMV kernel that produces Q, K, V from one dispatch. Then CPU reads results for attention scores. Then Metal encodes O_proj. This removes 3 sgemv call overheads and keeps the projection in a pipeline with MoE.

### R5. Metal Online Softmax Attention Scores
**Expected: -2 to -4ms at seq_len 50-100. Risk: Medium.**

`single_head_attention()` is pure scalar code — no BLAS, no SIMD. For 32 heads at seq_len=50: 32 × 50 × 128 = 204K multiply-adds in scalar loops.

A Metal kernel computing QK^T + softmax + V-weighted-sum for all 32 heads would parallelize across heads and sequence positions. uzu has this exact kernel (online softmax pattern).

## Recommended Execution Order

1. **R1 (batched QKV sgemv)** — simplest, lowest risk, immediate 2.4ms win
2. **R3 (eliminate allocations)** — easy refactor, 1.5ms win
3. **R5 (Metal attention scores)** — removes scalar bottleneck as seq_len grows
4. **R2+R4 hybrid (Metal projections + single cmd_buf)** — highest ceiling but most complex
